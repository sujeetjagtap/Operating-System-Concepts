Chapter 5 — CPU Scheduling

The lecture covers scheduling concepts and criteria, FCFS, SJF/SRTF, Round Robin, Priority, multilevel queues/feedback queues, multiprocessor scheduling, real-time scheduling and algorithm evaluation.

5.1 What is the scheduler deciding?

The CPU scheduler selects a process from the ready queue and allocates a CPU core to it. Scheduling decisions can occur when processes switch between running, waiting, ready, or termination states; the lecture distinguishes preemptive and nonpreemptive cases.

Think like the scheduler: “Several processes are waiting. Which one should run next, and what criterion should guide the choice?”

5.2 Scheduling criteria

CPU utilization

Keep CPU busy.

Throughput

Completed processes per unit time.

Turnaround

Time from submission to completion.

Waiting

Time spent waiting in the ready queue.

Response

Time until the first response.

Optimization generally seeks high utilization/throughput and low turnaround, waiting and response time.

FCFS — “Who came first?”

Processes run in arrival order. It is simple and non-preemptive. Example: if P1 needs 10 ms and P2 needs 2 ms, P2 waits behind P1 even though it is short. This can create the convoy effect.

SJF — “Who needs the least CPU time?”

Among available processes, choose the one with the shortest predicted next CPU burst. It is non-preemptive. Example: P1=10 ms, P2=2 ms, P3=4 ms → P2 runs first.

SRTF — “Who has the least time left?”

SRTF is the preemptive form of SJF. If a new process arrives whose remaining burst is shorter than the currently running process, the CPU can switch to the new process.

Round Robin — “Take turns”

Each ready process receives a fixed time quantum. Example with q=2 ms: P1 runs 2 ms, then P2 runs 2 ms, then P3, then back to P1 if work remains. A smaller quantum usually improves response but causes more context switches.

Priority — “Who has higher priority?”

Each process has a priority value. The CPU selects the highest-priority process; in the lecture's convention, a smaller integer means higher priority. It may be preemptive or non-preemptive. Aging can reduce starvation.

6.1 Why synchronization is necessary

Concurrent processes can be interrupted at any time. If they access shared data without coordination, the final value can depend on the order of operations. The lecture demonstrates this using a producer-consumer counter.

6.3 Peterson’s solution — understand flag and turn first

Peterson’s solution is a two-process method for protecting a critical section. Before looking at the code, understand the two shared pieces of information.

flag[2] = “Do I want to enter?”

There is one Boolean flag for each process:

  • flag[0] = true means P0 wants to enter the critical section.
  • flag[1] = true means P1 wants to enter the critical section.
  • false means that process is not currently trying to enter.
Think of flag as two “I am waiting” signs.

turn = “If both want in, who gets the chance?”

turn stores either 0 or 1. If both processes want to enter at the same time, it breaks the tie.

Think of turn as a “you go first” token.

Example: P0 sets flag[0]=true because it wants to enter. P1 does the same with flag[1]=true. They then use turn so that both cannot enter the critical section together. One gets the turn; the other waits until the first process leaves.

Why both variables? flag tells us whether someone wants to enter; turn helps decide who waits when both want to enter.

Then read the algorithm

flag[i] = true;
turn = j;
while (flag[j] && turn == j) { }

// critical section

flag[i] = false;

For P0, i=0 and j=1. P0 announces “I want in,” gives P1 the turn, and waits only while P1 also wants in and it is P1’s turn.

Select which processes want to enter.

6.5 Semaphore — think of it as a counter of permission

A semaphore can be used to coordinate access to shared resources. For a simple counting semaphore, wait() consumes one available permit and signal() returns one.

Chapter 8 — Deadlocks

8.1 What is a deadlock?

Imagine two people each holding something the other needs. Neither can continue, so neither releases what they hold. An OS deadlock is the resource-allocation version of this situation.

8.4 Compare the deadlock-handling approaches

ApproachCore questionBasic ideaEasy way to remember
PreventionCan we break a necessary condition?Design the system so at least one of the four necessary conditions cannot hold.“Stop the ingredients.”
AvoidanceIs this resource request safe?Grant requests only when the resulting state remains safe; Banker’s algorithm is the classic example.“Check before committing.”
DetectionHas deadlock already happened?Allow resource allocation, then run a detection method to find deadlock.“Let it happen, then detect.”
RecoveryWhat do we do after detection?Take recovery action such as terminating processes or preempting resources, depending on the system strategy.“Break the deadlock.”

8.4 Three strategies

Prevention

Restrict how requests can be made so at least one necessary condition cannot hold.

Avoidance

Examine each allocation and keep the system in a safe state.

Detection + Recovery

Allow deadlocks to occur, detect them, then recover.

The lecture also notes a fourth practical approach: some systems simply ignore the problem rather than continually paying the cost of sophisticated handling.

8.5 Safe vs unsafe — interactive mini-check

A safe state has an ordering in which every process can obtain what it still needs, finish, and release resources for the next process. An unsafe state means deadlock is possible, not that deadlock has already occurred.

8.6 Banker’s Algorithm — the banker's question

For multiple instances of resource types, the lecture introduces Banker’s algorithm. Its key data structures are Available, Max, Allocation, Need, with Need = Max − Allocation.

Imagine a bank: “If I grant this loan now, can every customer still eventually finish? If yes, the state is safe. If not, make the customer wait.”
